# Итерации реализации HTTP MCP

Этот документ детализирует [общий план](MCP_REMOTE_PLAN.md). Ветка: `feat/http-mcp`.
Статус всех итераций: запланировано. Каждая итерация должна завершаться рабочим, проверяемым результатом и отдельным коммитом или PR в форке.

Первый выпуск: чтение программ и изменение рабочих подходов/повторов в шаблоне программы. Исправление истории и изменение открытой на устройстве сессии остаются отдельными задачами.

## Последовательность

| Итерация | Результат | Зависимости |
|---|---|---|
| 1 | Зафиксированные контракты и требования клиента | — |
| 2 | Общий механизм записи профиля | 1 |
| 3 | Узкий API изменения программы | 2 |
| 4 | MCP с адаптерами данных и явным контекстом | 1 |
| 5 | OAuth и ограниченный доступ API | 1–3 |
| 6 | Streamable HTTP и инструменты чтения | 4–5 |
| 7 | Инструмент изменения программы | 3, 6 |
| 8 | Контейнер, HTTPS и подключение ChatGPT | 7 |

После итерации 1 работу над адаптерами можно вести независимо от извлечения механизма записи. Публичное развёртывание выполнять после готовности авторизации. Локальные проверки транспорта допустимы раньше с тестовой авторизацией, недоступной в production.

## 1. Контракты и проверка совместимости

**Цель:** снять неопределённость до реализации OAuth и транспорта.

**Изменения:**

- Сверить текущий upstream и ветку форка с кодом, на котором основан общий план.
- Зафиксировать версии Node.js, MCP SDK, протокола и официальные источники требований ChatGPT.
- Проверить возможность подключения кастомного MCP на целевом аккаунте; отдельно проверить доступность мобильного использования. Если проверка требует ещё не готовый сервер, зафиксировать это как отложенный критерий итерации 8.
- Выбрать stateless или stateful Streamable HTTP, тип ответов и способ регистрации OAuth-клиента по требованиям клиента.
- Описать `inputSchema` / `outputSchema`, API ошибки и правила повторов.
- Определить точные пределы `sets` / `reps` по интерфейсу; семантику диапазонов, прогрессии и повторов на сторону.
- Зафиксировать OAuth resource/audience и способ делегирования MCP → API. Предпочтительно обмен на короткоживущий внутренний токен; не использовать прозрачную пересылку токена с неверной audience.
- Решить, какие данные читает MCP: узкие endpoints или отдельный read endpoint профиля. Право `plan:read` не должно автоматически давать доступ ко всему профилю через `GET /api/data`. Если предпросмотру нужна история, задать отдельное право `training:read` или выполнить расчёт в API с ограниченным ответом.

**Артефакты:** новый `docs/MCP_REMOTE_CONTRACTS.md`, примеры запросов/ответов и таблица прав. Новые имена модулей ниже — предложения, уточняемые при реализации.

**Готово, когда:** нет неявных решений о пользователе, ресурсах токенов, формате конфликтов и хранении повторов; внешние ограничения клиента записаны.

## 2. Общий механизм сохранения профиля

**Цель:** сохранить одного писателя и существующие гарантии синхронизации.

**Изменения:**

- Выделить модуль хранилища, например `api/state-store.js`, из `api/server.js`.
- Сосредоточить чтение, сравнение ревизий, атомарную запись и инвалидацию кеша в одном механизме.
- Перевести существующий `PUT /api/data` на этот механизм без изменения внешнего контракта.
- Сохранить обработку `active`, reset stamps, media bookkeeping и текущую нормализацию состояния.
- Поддержать условную мутацию текущего документа для будущего PATCH. Между проверкой ревизии и записью не добавлять асинхронный разрыв без очереди по UID.
- Отдельно определить no-op: документ и ревизия остаются прежними.

**Проверка:** существующие API tests; две записи на одной ревизии дают один успех и один конфликт; новая ревизия сразу видна кешированным читателям; no-op не увеличивает её.

**Готово, когда:** прежний PUT работает через общий механизм, а второй процесс не пишет в `data`.

## 3. API изменения подходов и повторов

**Цель:** редактирование работает до подключения MCP.

**Изменения:**

- Добавить `PATCH /api/routines/{routineId}/exercises/{index}` на общий механизм записи.
- Принимать ожидаемые ревизию и exercise ID, а также одно или оба поля `sets` / `reps`. Индекс — с нуля.
- Проверять объект, режим `reps`, целые значения, диапазон повторов и дополнительные ограничения из итерации 1.
- Сохранять все остальные поля упражнения и профиля.
- Ставить отметки изменения программы/профиля, соответствующие существующему merge.
- Возвращать before/after, новую ревизию и точные идентификаторы. Не менять историю и `active`.
- Добавить `operation_id`: API хранит результат операции с привязкой к UID и хешу аргументов. Повтор с тем же ID возвращает первоначальный результат; тот же ID с другими аргументами отклоняется. Определить TTL и предел хранения. Результат и запись должны фиксироваться согласованно; выбрать механизм, выдерживающий рестарт, либо явно сузить гарантию.
- Обновить `api/openapi.yaml`.
- На этом этапе использовать существующую авторизацию для локальных проверок. Новые OAuth токены получают доступ только после итерации 5.

**Проверка:** 3×10 → 4×8; повтор операции; no-op; невалидные значения; повтор упражнения в программе; перестановка/удаление цели; stale revision; сохранение rest/weight/superset; параллельная запись новой тренировки из веб-клиента.

**Готово, когда:** endpoint не теряет чужие изменения и результат штатно виден в веб-приложении.

## 4. Рефакторинг MCP под два источника данных

**Цель:** убрать зависимость инструментов от глобального профиля, сохранив stdio.

**Изменения:**

- Выделить регистрацию инструментов и слой чистых вычислений.
- Ввести явный контекст вызова: источник данных, авторизованный пользователь, права, сигнал отмены.
- Сохранить файловый read-only адаптер для локального stdio.
- Добавить асинхронный HTTP-адаптер к API с заданным оператором base URL.
- Сделать обработчики асинхронными, ожидать `handler` через await.
- Разделить кеши по пользователю; не изменять глобальный UID между запросами.
- Упаковать необходимые Node-safe библиотеки для расчётов без React runtime.
- Добавить timeouts и нормализацию ошибок API; не выполнять автоматические повторы записи.

**Проверка:** прежние MCP tools tests; сравнение результатов локального и API-адаптеров на одной fixture; параллельные вызовы двух пользователей; отсутствие токенов в результатах и логах.

**Готово, когда:** stdio совместим, а инструменты можно вызвать через HTTP-адаптер без файлового доступа.

## 5. OAuth и делегирование к API

**Цель:** подключение внешнего клиента с ограниченными правами.

**Изменения:**

- Реализовать Authorization Code + PKCE, discovery metadata, регистрацию клиентов выбранным способом, redirect URI validation и resource/audience validation.
- Использовать существующий вход openGym и страницу согласия с перечнем прав.
- Добавить отдельные сущности OAuth grants/tokens; не превращать их в обычные мобильные session tokens.
- Реализовать срок жизни, отзыв, отключение пользователя и выбранный механизм refresh.
- Реализовать делегирование к API из итерации 1: внутренний токен ограничен пользователем, audience и scopes. Не выдавать MCP административный credential.
- Централизовать проверку прав API: OAuth-токен с узкими scopes не должен открывать существующие широкие маршруты.
- Добавить управление подключениями в интерфейсе и metadata защищённого MCP-ресурса.
- Не передавать client-controlled UID в качестве доверенного пользователя.

**Проверка:** полный authorization flow; reuse кода; неверные PKCE/redirect/audience; expired/revoked token; read-only token на запись; OAuth token на общий PUT профиля; изоляция профилей; отмена согласия.

**Готово, когда:** разрешённые операции доступны нужному пользователю, запрещённые не обходятся через другие endpoints.

## 6. Streamable HTTP с чтением

**Цель:** получить работающий удалённый MCP до включения записи.

**Изменения:**

- Добавить HTTP entrypoint в `mcp/src/` на официальном SDK.
- Подключить `initialize`, `tools/list`, `tools/call` и необходимые методы транспорта выбранной версии.
- Предоставить `list_routines`, `get_routine`, `preview_session` через API-адаптер.
- Авторизовать каждый запрос; при stateful режиме привязать сессию к пользователю и определить завершение/TTL.
- Возвращать схемы результатов, понятный текст и tool annotations.
- Добавить обработку неподдерживаемых версий, отмены, обрыва соединения и graceful shutdown.
- Ограничить тела запросов, concurrency, Origin/Host по принятой политике. Отсутствующий Origin у server-to-server клиента обрабатывать явно.
- Проверить JSON-ответы через MCP Inspector или другой совместимый клиент.

**Проверка:** handshake, список инструментов, чтение, предпросмотр, 401/discovery, неправильный пользовательский контекст, рестарт и завершение сессии.

**Готово, когда:** внешний MCP-клиент читает данные через авторизованный HTTP endpoint без volume данных.

## 7. MCP-инструмент изменения программы

**Цель:** полный сценарий чтение → выбор → изменение → предпросмотр.

**Изменения:**

- Добавить `update_routine_exercise` по контракту итерации 1, включая `operation_id`.
- Результаты чтения должны отдавать индекс, exercise ID и ревизию для точного последующего вызова.
- Не искать цель приблизительно внутри операции записи. Неоднозначный поиск возвращает кандидатов и `changed: false`.
- Обработать 409 как `conflict` с данными для перечитывания. Повтор после несвязанного изменения допустим только при доказанной неизменности цели; ограничить число повторов. Изменённую цель повторно согласовывать.
- Возвращать подтверждённое API before/after. Ошибку последующего preview не выдавать за неуспешное сохранение; явно сообщить, что изменение сохранено, а предпросмотр недоступен.
- Описать в инструментах поведение при `needs_clarification` / `conflict`; защита сервером не зависит от соблюдения этих инструкций моделью.
- Добавить annotations изменения и `outputSchema`.

**Проверка:** идентичные упражнения в разных программах; несколько вхождений в одной; потерянный ответ и повтор; конфликт цели; read-only scopes; следующий старт учитывает новый план и progression.

**Готово, когда:** успешное изменение проверяется в веб-приложении, а неоднозначность и конфликты не ведут к случайной записи.

## 8. Контейнер, публикация и приёмка ChatGPT

**Цель:** воспроизводимый запуск и подтверждённый целевой сценарий.

**Изменения:**

- Добавить Dockerfile MCP, отдельный compose profile и healthcheck.
- Запускать контейнер без data volume, непривилегированно; не хранить пользовательские credentials в образе.
- Настроить nginx маршруты `/mcp` и OAuth/discovery, HTTPS, proxy trust и timeouts. Если SSE не используется, не добавлять его ради названия транспорта.
- Обновить `.env.example`, self-hosting guide и MCP README: запуск, callback URLs, права, отзыв, диагностика.
- Добавить нужные suites и сборку образа в CI.
- Проверить, что обычный compose без MCP profile сохраняет прежнее поведение.
- Подключить приложение в ChatGPT и проверить чтение/изменение с веб- и мобильного клиента на целевом аккаунте.
- Зафиксировать реальные ограничения тарифа/клиента и результат smoke check; не считать мобильную совместимость доказанной по тесту Inspector.

**Проверка:** контейнер → API, OAuth через HTTPS/proxy, отказ API, restart, отсутствие доступа к data, стандартная установка; фраза «В программе Push поставь жим 4×8» приводит к изменению нужного шаблона и корректному ответу.

**Готово, когда:** есть инструкции воспроизводимого запуска и подтверждение целевого подключения. Если мобильный клиент не поддерживает сценарий, выпуск описывается как HTTP MCP с явным ограничением клиента.

## Сквозные правила

- API — единственный писатель. Все новые пути изменения используют одну проверку ревизии и запись.
- Программа и выполненная тренировка — разные объекты; первая итерация записи не исправляет историю.
- Не переписывать весь state из MCP без необходимости.
- Ошибки авторизации, неоднозначность, конфликты и сетевые ошибки имеют разные результаты.
- Существующий merge выбирает последнюю редакцию целой программы. Его ограничение сохраняется и должно быть проверено/описано; слияние по отдельным полям — отдельная задача.
- После каждой итерации запускать соответствующие существующие suites и добавлять проверки новых границ поведения.
- Не публиковать upstream PR и не развёртывать публичный сервис автоматически в рамках подготовки этих документов.
