# План: удалённый MCP для openGym

Дата: 2026-10-06. Исходный проект: https://github.com/DuarteSantos8/openGym.
Основа анализа: main, коммит `1350409a7b15ff8ce5690c18b530cfba62d80f46`.
Статус: проектирование; реализация и развёртывание не выполнены.

## Цель и границы первого выпуска

Подключать openGym к ChatGPT, включая мобильный клиент там, где аккаунт и клиент поддерживают кастомные MCP-приложения. Ассистент читает программы и меняет количество рабочих подходов и повторов выбранного упражнения. Перед реализацией подтвердить доступность подключения на целевом аккаунте и актуальные требования ChatGPT к транспорту и OAuth.

Первый выпуск изменяет сохранённый шаблон программы (`routines[].ex[]`), а не историю и не текущую сессию. Текущая сессия `active` хранится на устройстве и удаляется сервером при сохранении профиля. Исправление истории — отдельное расширение с переиспользованием `session-edit.js` и пересчётом объёма, PR и рабочих весов.

## Архитектура

```text
ChatGPT → публичный HTTPS /mcp → отдельный MCP-контейнер
                                      ↓ HTTP, внутренний пользовательский токен
                                openGym API → ./data

ChatGPT → OAuth endpoints → вход openGym / согласие пользователя
```

MCP-контейнер не получает volume `data`, секрет подписи сессий или административный ключ. API остаётся единственным писателем профилей. Каждое обращение содержит пользовательский контекст; глобальный `OPENGYM_UID` остаётся только в существующем локальном режиме stdio.

Для удалённого транспорта использовать официальный SDK и Streamable HTTP, начиная с коротких JSON-ответов. Сохранить локальный stdio-режим чтения. Выделить общую регистрацию инструментов и адаптер источника данных: локальные файлы для stdio, API для HTTP. Проверить совместимость расчётов и существующих инструментов чтения; HTTP-контейнер должен иметь нужные чистые библиотеки, но не всё приложение.

## Этап 0. Проверка совместимости

- Зафиксировать версии MCP SDK, протокола и Node.js; сверить требования ChatGPT с актуальной официальной документацией.
- Проверить создание кастомного приложения на аккаунте пользователя, OAuth-подключение и использование на мобильном клиенте. Это критерий выпуска, а не предполагаемая гарантия.
- Уточнить требования к регистрации OAuth-клиента: предварительная регистрация или динамическая, допустимые redirect URI, discovery и resource indicators.
- Проверить актуальную ветку upstream перед началом реализации; провести проверку существующей авторизации API, синхронизации и упаковки общих библиотек.

Результат: короткий документ совместимости и согласованный минимальный набор инструментов.

## Этап 1. API для MCP

Вынести из `api/server.js` общий механизм записи состояния: чтение, проверка ревизии, изменение, увеличение `_rev`, атомарная запись, инвалидация кеша и существующее обслуживание media. И обычный PUT профиля, и новый endpoint используют этот механизм. Между проверкой ревизии и записью не добавлять await без сериализации операций по пользователю.

Предлагаемый endpoint: `PATCH /api/routines/{routineId}/exercises/{index}`. Запрос содержит `sets`, `reps`, ожидаемую ревизию и ожидаемый exercise ID для защиты от изменения порядка. Индекс отсчитывается от нуля; один exercise ID может встречаться несколько раз.

- Определять профиль по токену, проверять права `plan:read` / `plan:write`.
- Проверять существование программы и позиции; запретить незаметное создание объекта.
- Принимать положительные целые значения в пределах, согласованных с интерфейсом.
- В первом выпуске поддержать режим `reps`. Проверять совместимость с `repsMin`, правилами прогрессии и односторонними упражнениями. Хранить повторы по существующему соглашению приложения; не угадывать «на каждую сторону».
- Изменять только переданные поля, сохранять вес, rest, superset, progression и остальные настройки.
- Ставить `_ts` изменённой программы и профиля по правилам существующей синхронизации; no-op не должен создавать лишнюю редакцию.
- На конфликт отвечать 409; MCP перечитывает состояние и повторяет только при неизменности целевого объекта. Изменённый объект требует нового решения пользователя.
- Возвращать фактическое before/after, новую ревизию и данные для предпросмотра следующей сессии.
- Обновить OpenAPI.

Результат: редактирование программы работает независимо от MCP и корректно синхронизируется с веб-клиентом.

## Этап 2. OAuth и пользовательский контекст

Реализовать OAuth-поток, совместимый с требованиями MCP и ChatGPT: Authorization Code + PKCE, metadata авторизационного сервера и защищённого ресурса, проверка redirect URI и audience/resource, сроки жизни и отзыв токенов. Поддержку refresh tokens и регистрации клиентов выбрать по результатам этапа 0.

Вход использует существующий механизм openGym, включая passkeys. На странице согласия пользователь видит выбранный профиль и права чтения/изменения программы. Новые OAuth-токены не следует считать эквивалентными существующим мобильным session tokens: нужен явный тип токена и ограничение прав по маршрутам. OAuth access token предназначен MCP-ресурсу: не передавать его автоматически в API с другой audience. Для MCP → API определить обмен на внутренний пользовательский токен с отдельной audience и ограниченными правами либо документированную общую границу ресурса. API проверяет токен, пользователя и права самостоятельно.

Добавить просмотр и отзыв подключений в настройках, учесть отключение пользователя и общий выход из аккаунта. Не писать токены в логи. Пользовательский контекст передавать явно, кеши разделить по UID.

Результат: два пользователя изолированы; отзыв доступа прекращает чтение и запись.

## Этап 3. Инструменты и HTTP MCP

Минимальные инструменты: `list_routines`, `get_routine`, `preview_session`, `update_routine_exercise`. Остальные существующие инструменты чтения подключать после проверки адаптера API.

Пример аргументов записи:

```json
{
  "routine_id": "push",
  "exercise_index": 0,
  "expected_exercise_id": "exercise-id",
  "expected_rev": 12,
  "sets": 4,
  "reps": 8
}
```

Определить `inputSchema` и `outputSchema`. Результаты: `success`, `needs_clarification`, `conflict`; реальные сбои выполнения — `isError`. Пользовательские статусы являются контрактом инструментов, а не статусами протокола MCP. Structured content сопровождать понятным текстом.

Поиск возвращает кандидатов с точными идентификаторами. Запись требует точную позицию и проверки ожиданий. При неоднозначности ничего не сохраняется: ChatGPT уточняет выбор и делает новый вызов. В описание инструментов включить семантику статусов и правила выбора. Не полагаться на правильность поведения модели как на защиту данных.

В `mcp/src/index.js` ожидать асинхронный handler через await. Добавить корректные timeouts, отмену, завершение и классификацию ошибок API. Проверить повтор запроса после потери ответа: установка абсолютных значений должна быть безопасной; для восстановления результата после уже совершённой операции предусмотреть operation ID/idempotency key с привязкой к пользователю и аргументам.

Объявить MCP annotations, включая чтение и изменение, где применимо. Выбор пользователем кандидата не считать универсальной гарантией подтверждения записи клиентом; сервер проверяет права и точность цели независимо.

Результат: вызовы читают и изменяют только нужный профиль; повтор не вызывает побочных изменений.

## Этап 4. Контейнер и публикация endpoint

- Добавить отдельный Dockerfile и опциональный compose profile для MCP; базовая установка не запускает сервис автоматически.
- Настроить `/mcp` через nginx с публичным HTTPS; доступ к API внутри Docker-сети.
- Использовать явный allowlist Origin и корректный адрес привязки, ограничения размера запросов, частоты и соединений; проверить защиту от DNS rebinding.
- Запускать контейнер непривилегированно, без data volume, по возможности с read-only root filesystem.
- Не принимать произвольный API URL из аргументов инструмента; адрес API задаётся оператором.
- Если используются MCP-сессии, session ID не заменяет авторизацию; проверить привязку сессии к пользователю и поведение после рестарта. Выбор stateless/stateful режима подтвердить проверкой клиента.
- Документировать HTTPS, OAuth URLs, proxy trust, конфигурацию домена, healthchecks, логи с request ID и безопасный отзыв доступа.

Результат: воспроизводимый запуск отдельного контейнера и подключение через внешний домен.

## Этап 5. Проверка и приёмка

Проверки должны охватывать реальные границы поведения:

- 3×10 → 4×8 сохраняется и отображается в веб-приложении после штатного обновления.
- `preview_session` учитывает изменение и действующие правила прогрессии; изменение программы не обещает отключить progression.
- Вес, диапазон, superset и другие настройки сохраняются; невалидный запрос ничего не меняет.
- Удаление/перестановка упражнения после чтения приводит к конфликту, а не изменению другого упражнения.
- Одновременная запись веб-клиента и MCP не теряет новую тренировку; проверить и существующее ограничение merge по целой программе при параллельных правках.
- Разные пользователи и параллельные запросы не смешивают данные; read-only token не пишет, отозванный token не работает.
- Ошибки API, обрыв ответа, повторы, рестарт контейнера и no-op дают корректные результаты.
- Локальные stdio tools и текущие API/frontend suites продолжают работать.
- Реальное подключение и вызов изменения из мобильного ChatGPT на целевом аккаунте; если клиент недоступен, явно зафиксировать ограничение вместо заявления о готовности.
